Convert a DNG to JPG in the browser

A DNG from Adobe’s converter, Apple ProRAW, a phone or a drone can be dropped straight into the browser window, developed and exported as a JPEG. Decoding runs on your machine; nothing is uploaded.

Updated 2026-11-255 min read

Open a DNG in the browser — no install, no upload

Drop the DNG into the browser window — or press PHOTO in the bottom-left corner — and the picture appears. Decoding runs in a Web Worker, development and rendering happen on the GPU, and the photo is never uploaded to a server: there is no account, no email and no “upload to convert” step. When the grade looks right, export a full-resolution JPEG.

It also does not depend on a raw codec installed on the computer: the decoder is a WebAssembly module loaded with the page. So a different laptop, a locked-down work account or a borrowed machine all open the same file the same way. The first RAW open downloads about 3.4 MB of decoder, cached by the browser afterwards.

What a DNG file is

DNG (Digital Negative) is Adobe’s openly documented raw container, built on TIFF/EP. Its point is that any software can read it from a public specification instead of reverse-engineering each camera’s private format. It is both a native camera format — Leica and Pentax bodies can record DNG directly — and the output of many conversion tools.

Apple ProRAW files are DNGs: Apple offers ProRAW on iPhone 12 Pro and later Pro models, and the container holds the sensor data plus Apple’s computational-photography metadata. Many Android phones output DNG through the Camera2 RAW API and some drones write DNG directly; they all take this page’s workflow.

This page also covers Apple ProRAW and the DNG files written by phones and drones: same container, different provenance and metadata.

DNGs from different sources are not laid out the same way

DNG is a container specification, not one fixed data layout: a camera-native DNG, a file converted by Adobe DNG Converter, a multi-frame DNG from a phone and a DNG from a drone can organise their data and metadata differently. Some carry raw sensor data that needs demosaicing; others are already linearised. This page does not split them by origin — they all go through the DNG decode path — and if a file’s structure is outside what the decoder handles, the embedded camera JPEG is the fallback, provided the file carries a camera preview large enough to use.

What the pipeline does to it

The decoder (flashraw compiled to WebAssembly) runs in a Web Worker and performs unpacking, demosaicing, camera white balance and the camera colour matrix. The result is decoded at 16 bits with four stops of scene headroom kept above white, then re-encoded as scene-linear half floats for the GPU; WebGL2 maps that linear data to the screen in real time. The headroom is why the highlights slider behaves like a raw processor rather than a JPEG editor: it compresses real above-white sensor data back into visible gradation instead of clipping what it never had.

The display transform is darktable’s sigmoid (jandren, merged for darktable 4.2): monotone on 0…∞, asymptotic to the white target instead of clipping, computed per channel with hue preservation and fitted in closed form. The repository’s npm run test:tone:reference renders a synthetic 128×512 linear EV ramp through an isolated darktable 5.6.2 CLI to a 16-bit PNG and compares pixels; the observed maximum linear-light error is 0.0014772 (test limit 0.0016). That validates the sigmoid curve, not a full camera RAW decode or Lightroom’s Auto algorithm.

The 64 built-in looks sit after the display transform: a LUT reads display-space values, so it changes colour and contrast relationships but is not what rescues a highlight. Each stage and the measured numbers are covered in the RAW-in-the-browser guide.

When a frame cannot be unpacked

Not every file unpacks completely. If the decoder cannot unpack the frame, or returns a truncated one, the page does not show half a black photo and does not fail outright: it falls back to the camera JPEG embedded in the file. You can still grade it, apply a look and export a JPEG, but it is the camera’s JPEG, not a 16-bit linear development — the above-white part was already compressed by the camera’s own display curve.

That is the difference between the two paths: when decoding works, editing and export start from real scene-linear data; on the fallback, the starting point is a JPEG the camera already processed. The fallback is not hidden and it is not called “full decoding” — whether a file decodes depends on the file and on the current decoder.

What you can and cannot do

You can open one RAW, develop it on the pipeline above, apply one built-in look (or stack a second) and export a full-resolution JPEG.

  • One frame at a time. There is no batch queue, no library, no ratings, keywords or cloud catalogue.
  • WebGL2 is required. Without WebGL2 the editor cannot render; this is not a slow CPU fallback.
  • No .xmp presets. Standard .cube LUTs can be imported instead.
  • Preview is capped at 4096 px on the long edge; export is not — it renders the in-memory full-resolution frame in tiles.
  • The first RAW open downloads about 3.4 MB of decoder, served from the browser cache afterwards.
