How precise does a LUT have to be before the difference disappears

A LUT’s precision is its cube edge: 17³ holds 4,913 nodes, 33³ holds 35,937. We ran one photo-derived query set through four sizes, and the answer is not “bigger is better” — it is “match the cube the look was authored on”.

Updated 2026-11-196 min read

How it was measured

The reference is the authored 33³ cube. The look was resampled to 17³, 21³ and 25³, then sampled with trilinear interpolation at query points taken from real photographs. Every channel was compared against the authored cube, in code values of 0–255 rather than percentages. What is under test is the colour response of these looks — not a monitor and not a camera.

The gap between mean and maximum is the part that matters. At 17³ the mean is 0.226 of a code value, so a typical pixel looks fine; the maximum of 20.8 is more than enough to leave visible steps across a smooth sky gradient. 21³ halves the worst case to 11.6, 25³ sits at 11.3, and 33³ takes both numbers to zero. A comfortable average does not mean a safe worst case.

Error lives where the curve bends hardest

Trilinear interpolation takes the eight surrounding nodes and weights them by distance. If the mapping between those nodes is a straight line, the result is exact; if it bends — a shadow toe, a highlight shoulder, near-saturated red, a hue that has been rotated — averaging pulls the bend straight. The error grows roughly with curvature times the square of the node spacing, so halving the spacing should cut it to about a quarter in smooth regions.

That also explains why mean and maximum are two orders of magnitude apart. Most pixels in a photograph sit in the midtones, where the response is close to linear, and that is where the 0.226 mean at 17³ comes from. The maximum lands on the few colours that sit near a kink: a wide gradient in the sky, a saturated red, the first values above black. Those are also exactly the places where a fixed step in a smooth ramp is easy to see, which is why the mean flatters a small cube.

Why 33³ has zero error

Because these 64 looks were authored at 33³ in the first place: every .cube in the repository is LUT_3D_SIZE 33 with exactly 35,937 rows. Compare 33³ with 33³ and the query lands on the numbers the author wrote — the difference is zero. It is exact not because the edge is large enough, but because it is the source data.

One nuance is easy to miss: a real pixel almost never lands on a node, so the GPU interpolates trilinearly all the time. That is not error, it is the definition of a 3D LUT — writing 33³ nodes is a statement that everything between them should be read linearly. “Zero error” means agreement with the authored data, not the absence of interpolation on screen.

Why 65³ buys nothing visible

A 65³ look has 274,625 nodes, 7.6 times as many as 33³. Across 64 looks that is roughly 52 MB of raw data before compression, which every download, inflate and GPU upload has to pay for — and the extra information is zero. It is the same authored data sampled more densely, so it cannot get closer to the source than 33³ already is. Once the error against the authored cube is zero, more nodes only draw the same polyline in finer ink.

On the web there is a second cost: the LUT is uploaded as a 3D texture, and doubling the edge multiplies its texture memory by eight. Nobody sees the extra interpolation accuracy; everybody pays the bandwidth.

Why 33³ costs only 1.34 MB: delta coding

The raw size of 33³ is not small: 35,937 nodes × 4 bytes × 64 looks ≈ 9.2 MB. It fits in a 1.34 MB gzip pack because a LUT is a smooth 3D gradient, and neighbouring samples along a row usually differ by only a few code values. The pack stores each sample as its difference from the neighbour to the left, gzips the diffs, and shrinks the payload from 9,199,880 bytes to 1,342,919 bytes; the decoder adds the diffs back losslessly. A small header records the edge and look count, so a stale pack can be rejected instead of feeding bad data to the shader.

The 64 looks are decoded lazily in the browser: only the look you select is inflated, at about 2 ms per look. The 1.34 MB is the network payload, not resident texture memory — cubes are uploaded on demand, and one 33³ cube is about 140 KB of GPU texture.

So how big should a web LUT be

17³
smallest pack, mean under 1 code value, max 20.8, banding risk on gradients
21³
worst case halved to 11.6, pack around 1.2 MB gzip
33³
zero error against the authored cube, 1.34 MB gzip
65³
about 52 MB for 64 looks, nothing visible gained

The decision follows the source cube. If the look was authored at 33³, do not drop to 21³ to save a few hundred kilobytes: with delta coding the whole 33³ pack is only slightly larger than the 21³ one, while the worst-case error goes from 11.6 code values to zero. If the source really is 17³, resampling it to 33³ does not make it accurate — it only makes the file bigger. Spend size where the information actually is.
