LUT 是一张颜色对照表，不是一层滤镜

LUT（look-up table，查找表）把一组输入颜色换成另一组输出颜色。1D 和 3D 能做的事差很远，厂商 LUT 还要求输入是 LOG 编码；前提弄错，画面会发暗、发硬而且偏色。

更新 2026-11-197 分钟

一张表：输入颜色进，输出颜色出

3D LUT 是一块立方体数据，三条轴都是 0–1 的 RGB 取值，边长 n 表示每个通道被切成 n 个节点，所以整块表有 n³ 个节点。渲染时，像素的 RGB 在立方体里定位，读出周围 8 个节点的值，用三线性插值算出一个新的 RGB。它不改变结构、不改变锐度，只改变颜色落在哪儿。

行业通用的交换格式是 .cube，纯文本：

TITLE "奶油高光"
LUT_3D_SIZE 33
DOMAIN_MIN 0 0 0
DOMAIN_MAX 1 1 1
0.07830 0.07540 0.07112
…

LUT_3D_SIZE 33 表示边长 33，文件里就要有 35,937 行 RGB 数值；DOMAIN_MIN / DOMAIN_MAX 声明输入范围，通常是 0–1。数据行的顺序是 R 变化最快、其次 G、最后 B。1D LUT 用 LUT_1D_SIZE，行数少得多：n 行 RGB 数值，三个通道各查一条曲线。

这个编辑器支持 3D LUT（LUT_3D_SIZE 2–128）和 1D LUT，导入时会在本地解析：.cube 是一段文本，可能带 UTF-8 BOM；解析后存进浏览器的 IndexedDB，文件不经过任何服务器（细节见隐私说明）。1D 会被烘到一张 33³ 的网格上，这样渲染器只需要处理一种数据。

1D 和 3D 差在哪

1D LUT3D LUT
数据每个通道一张曲线，n 个采样点n³ 个 RGB 三元组，33³ 是 35,937 个
怎么查表三个通道各查各的：f(R)、g(G)、h(B)用 RGB 一起定位，三线性插值
能做什么黑位、白位、gamma、单通道偏移这类逐通道曲线任意颜色映射：色相旋转、去饱和、胶片式交叉染色、色域压缩
做不到什么跨通道效果：单独抽掉某个色相、把彩色转成黑白不增加信息；节点之间仍然靠插值得到

关键区别在「通道之间能不能互相影响」。1D LUT 对 R、G、B 分别算，红色通道的结果永远不会参考绿色；胶片那种红往青里跑、蓝色高光偏暖的交叉染色，以及把画面真正压成黑白（三个通道按亮度重新分配），都必须有 3D LUT 才能表达。所以内置的 64 款 look 全部是 33³ 的立方体，测量它们的精度时量的也是 3D 立方体。

为什么厂商 LUT 要 LOG 输入，直接套普通照片会怎样

LOG 是一种把场景亮度摊开的编码：它把暗部抬起来，让 0–1 的码值装下远超显示范围的动态范围，而不是像 sRGB 那样按显示对比度分配。相机厂商发布的 F-Log、F-Log2、V-Log LUT，都是针对「已经按对应 LOG 曲线编码的输入」设计的——表里的每个输入码值都对应一个明确的场景亮度。

普通照片是显示编码的 sRGB。同一档暗部亮度，在 LOG 编码里的码值比 sRGB 里高得多。把 LOG LUT 直接套上去，相当于告诉它「这些暗部比你想象的暗得多」，出来的画面就会整体发暗、暗部发死，颜色也会因为查表位置错位而偏掉或过饱和。这不是 LUT 做错了，是输入条件不成立。

这个编辑器在套 LUT 之前有一个输入色彩空间选项：sRGB、F-Log、F-Log2、V-Log。选 LOG 时，它先把显示值转回线性，再按对应 LOG 的公开传递函数重新编码，然后才查表；导入的 .cube 文件名或标题里带 F-Log / V-Log 时，这个选项会自动切过去。色域仍按 sRGB 处理，所以厂商 LUT 的结果是接近，而不是逐字节一致。

强度滑块到底在混什么

这一步的公式很简单：mix(v, lut(v), strength)。强度 0 时输出等于输入，100 时输出完全等于查表结果，中间就是两个数值之间的一条直线。它不是「把 LUT 的参数改小」，而是按比例把原图和调色结果兑在一起。

所以重口味的 look 拉到 50% 不会变成一款温和的 look，只会变成一张「一半原色、一半风格」的画面：对比被稀释，饱和度显得更平。厂商 LOG LUT 用在普通照片上时，编辑器给的建议强度是 30–60%，原因就在这儿——先小剂量找回一点风格，别指望一张为 LOG 设计的表在 sRGB 上等效。

叠两款 look 时，每一层都各自混一次，A 的结果是 B 的输入；这套顺序和混合方式会被原样烘进合并出来的 .cube，具体做法见合并 LUT。

LUT 救不回已经死白的高光

LUT 是逐像素换色：它读一个现有的 RGB，吐出另一个 RGB。如果一个像素的三个通道都已经卡在 1.0，它在表里只能被映射成某个固定的输出值——整块死白区域都会变成同一种颜色，里面本来有的天空层次、云、灯泡边缘，LUT 一个也变不出来。同理，它也修不了白平衡失准的片子：单个通道被裁掉之后，那个通道的信息已经没了。查表时输入还会被截断（clamp）到 0–1，超过 1 的数据在 LUT 这一层不被考虑。

这就是为什么这个编辑器先跑完整条 RAW 管线：RAW 按 16 位解码，保留 4 档高于白的场景余量，显示变换用 darktable 的 sigmoid——在 0…∞ 上单调、渐近逼近白点而不裁切，高光是被压缩进可见范围，而不是被砍掉。显影完、映射到显示空间之后，LUT 才接手。处理顺序见在浏览器里打开 RAW。

在这台编辑器里，LUT 排在管线的哪一步

  1. 解码与显影。RAW 在 Web Worker 里解成 16 位场景线性帧，曝光、白平衡、高光阴影都在线性空间处理，真实的高于白数据还在。
  2. 显示变换。sigmoid 把场景线性压缩到 0–1 的显示值，保持单调，不裁切。
  3. 输入色彩空间（可选）。套厂商 LOG LUT 时，把显示值按对应 LOG 曲线重新编码。
  4. LUT。A 槽位按强度混合，开了双 LUT 再走 B 槽位；两者都按 mix(v, lut(v), s) 执行。
  5. 导出。JPEG 按 50 / 75 / 100% 源图长边渲染，和屏幕共用同一条管线。

看懂这几个前提，再回头用 64 款内置 look 或导入自己的 .cube，就大致能预判一个 LUT 在你手头的素材上是否成立。想直接验证，打开编辑器拖一张 RAW 进去，把同一款 look 的强度从 100 拉到 0 看一遍就行。
